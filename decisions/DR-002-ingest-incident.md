# DR-002 · 全量重建事故与恢复（P0 实施记录）

> 阶段：P0 · 日期：2026-10-05 · 状态：**已恢复**（零重复 embedding 调用）
> 关联：DR-001（依赖迁移）；本记录与"负结果同样留档"的评测纪律一致

## 事件

全量重建（105 篇 + 2 中文文档，按量付费 embedding）进行到第 91 篇
`2605.06609__2026-05-07` 时触发编码错误并级联失败：
- 该论文 PDF 的数学字体抽取产生**孤立代理项字符**（U+D835，共 115 处，5 个子块受影响）；
- 嵌入请求体序列化（UTF-8 编码）时抛 `UnicodeEncodeError: surrogates not allowed`，
  该文档未入库；但其**父块已先进入内存** → 其后每篇文档的 `store.save()` 都在
  `parent_store.json` 写盘处失败（17 篇被逐文档捕获标记为 failed，批次未中断）。

磁盘终态：`index.faiss`（32,501 行）与 `child_docs.json`（32,501 条，含除毒文档外全部 106 篇）
完好；`parent_store / manifest / meta / tokenized` 停留在中途。

## 根因（三点，均已修复）

1. **清洗范围缺口**：孤立代理项（非法 Unicode 标量值）不在零宽/控制符剥离范围内。
2. **落盘非原子**：`write_text` 先截断再编码，编码异常直接毁掉既有 JSON 文件。
3. **内存变更早于外部调用成功**：`add_document` 先写 parents 再嵌入 children，
   单文档失败把毒数据留在内存，放大到后续所有 save。

## 恢复（不重复任何 embedding 调用）

`scripts/repair_index.py`：以 `child_docs.json`（行号真相）为准 →
对全部已入库文档做**确定性重分块**（同一 loader/chunker/清洗）→
**逐块 sha1 对照 100% 一致（32,501/32,501）** 后才原子重写缺失文件 →
`verify_store: ok=True`（106 docs / 32,501 chunks / dim=1024）。
毒文档 `2605.06609` 按用户决定**剔除**（如需纳入：修复后单篇 ingest，约 ¥0.01）。

## 费用

全量首跑 3,482,019 tokens ≈ **¥0.44**（含至第 90 篇）；恢复零新增调用。
（按量付费余额 5 元，余量充足。）

## 教训（进 P1 语料体检报告素材）

- "逐文档异常捕获 + 逐文档落盘 + 追加式索引"的事故设计有效：损伤面被限制在
  每文档一个 save 周期内，且核心行号真相文件完好 —— **离线可重建性**（确定性分块）
  是恢复的关键前提（这也验证了 P0 分块器与索引设计的价值）。
- 语料质量是评测可信度的上限：本事故是"文档清洗"章节的一手案例
  （全语料扫描：仅 1 篇含代理项；零宽/控制符广泛存在，明细见 manifest 的 `sanitize_removed`）。
